ФИНАЛЬНЫЙ ПЛАН РЕАЛИЗАЦИИ ПРОЕКТА "SPACEBATTLE" (ООАиП), вер. 2
БОЙ + СЕРВЕРНАЯ ЧАСТЬ (лобби, матчмейкинг)
================================================================================
1. ЦЕЛИ И ОБЩИЙ КОНТЕКСТ
- Платформа: .NET 10, решение space-battle.slnx (SpaceBattle.Lib + тесты).
  Добавляются модули: SpaceBattle.Server, SpaceBattle.Runner, SpaceBattle.Bots.
- Задача: реализовать бой по правилам И серверную часть: лобби, матчмейкинг
  с учётом истории боёв, программы игроков, наблюдение за боем.
- Основной сценарий: запуск сервера (консольная оболочка) -> каталог правил ->
  игроки подают заявки (бот + правила, на которые согласны) -> матчмейкинг по
  истории боёв собирает матч -> событие "Матч готов" -> сессия боя в своём
  IoC-scope -> такты: приказы программ игроков -> действия и реакции -> события
  в Event Store -> наблюдатель видит кадры в консоли -> конец боя (весь флот
  соперника выведен из строя или лимит тактов) -> результат в историю ->
  игроки возвращаются в лобби.
- Принципы: SOLID; IoC с единой точкой сборки; сессия = дочерний scope;
  сервер не знает об оболочках (консоль/веб поверх); ядро не знает предметной
  области; код не удаляется; регистрация пользователей и рейтинг НЕ входят в
  объём [решено] — матчмейкинг опирается только на историю боёв;
  тесты 90% строк / 100% ветвлений, сгенерированный код исключён атрибутом.
---
2. ПОШАГОВЫЙ ПЛАН РЕАЛИЗАЦИИ
БЛОК А. БОЙ (порядок этапов фиксирован, по proposal раздел 11)
ЭТАП 1: Разбор и проверка правил
- Парсер трёх видов записей: "X - Y", "Тип может Действие",
  "Действие включает в себя Элемент" + записи реакций (формат на Этапе 5).
- Валидатор: команда существует в коде, состав действия непустой, нет циклов,
  реакция ссылается на существующие событие и действие.
- Ошибки: список с номерами строк, игра не запускается [решено].
ЭТАП 2: Фабрики адаптеров и стратегии доступа (ЛР5)
- Composition Root в точке запуска: RegisterIoCDependency* вызываются из
  одного места, а не из классов.
- Source generator: одна фабрика на интерфейс (IMovingFactory и т.д.);
  фабрика получает стратегию доступа к IDictionary<string,object>.
- Кастомные стратегии через [Adapter(typeof(IMovingObject),"Velocity",Class.Method)].
- Сгенерированный код помечается [GeneratedCode] и исключается из покрытия CI.
ЭТАП 3: Сборка сессии
- Описание игры — неизменяемый объект после проверки; переиспользуется сессиями.
- Сессия = дочерний IoC-scope: составы действий по правилам, сущности, владельцы;
  общее (фабрики, стратегии, каталог команд) — в корневом scope.
- Результат: правила А и правила Б из одних команд дают разное поведение (тест).
ЭТАП 4: Механики корабля
- BurnFuelCommand, RefuelCommand (заправщик), RepairCommand (ремонтник);
  каждая команда — тест на поведение.
- Метеорит = тип в правилах с действием движения без топлива, новых команд нет.
ЭТАП 5: Реакции на события
- Формат записи реакции: "При Событии X Выполнить Y", Y — действие из правил,
  применяется к участникам события.
- Такт: фаза 1 — назначенные и не остановленные действия; фаза 2 — реакции на
  события предыдущего такта. Исключение команды -> ExceptionHandler, сессия живёт.
- Результат: при столкновении выполняется реакция из правил (тест).
ЭТАП 6: Запуск боя (режим battle точки запуска)
- CLI: dotnet run --project SpaceBattle.Runner -- battle --rules rules.txt
  --scenario scenario.txt --ticks N.
- Начальное состояние — отдельный файл сценария (сущность, владелец, свойства).
- Остановка: весь флот соперника выведен из строя (курс) ИЛИ лимит тактов = ничья.
- Результат: команда запуска проводит игру от начала до конца и выводит итог.
БЛОК Б. СЕРВЕРНАЯ ЧАСТЬ (объём команды по указанию преподавателя)
ЭТАП 7: Лобби
- Заявка: игрок (имя/токен, без регистрации), rulesetId, botId;
  статусы Waiting/Ready/Matched/Withdrawn.
- Операции: Submit, ConfirmReadiness, Withdraw, OptOut ("прекратить участие
  в боях" — больше не назначается). Всё in-memory, за интерфейсом ILobby.
- Каталог ruleset'ов: сервер загружает файлы правил, игрок выбирает согласные.
ЭТАП 8: История боёв и матчмейкинг
- История: append-only хранилище результатов (кто, с кем, правила, места).
  Рейтинга нет [решено]; история — вход матчмейкинга ("с учётом истории", курс).
- Политика v1 за IMatchmakingPolicy: группировка по ruleset; пара — давно не
  встречавшиеся / близкие по числу боёв; нечётный ждёт; opt-out исключён;
  повтор пары подряд избегается. Событие "Матч готов" -> StartMatch.
ЭТАП 9: Программы игроков и приказы
- IPlayerController: приказы по взгляду на бой за такт. v1 — C#-боты в
  репозитории (Агрессор, Танкер); позже — загрузка сборок тем же интерфейсом.
- Взгляд для бота — проекция read model через IGameItem.GetProperty: свой флот
  и видимый противник.
- Приказ (start/stop/мгновенное действие по имени из правил) -> IDictionary
  order -> Actions.Start/Stop -> AuthCommand.
- Связь "Пользователь - Корабль" = владение конкретными сущностями в сессии;
  AuthCommand проверяет приказ по этому владению.
ЭТАП 10: Хост боя
- Жизненный цикл матча: scope сессии -> сущности из сценария -> привязка
  владельцев -> цикл тактов (сбор приказов, фазы 1-2, DrainEvents ->
  EventStore.Append, проверка останова) -> результат в историю -> заявки
  возвращаются в лобби.
ЭТАП 11: Оркестратор сервера и консольная оболочка
- Модуль SpaceBattle.Server: лобби, матчмейкинг, хост, история, Event Store;
  об оболочках не знает [решено].
- Оболочка в Runner (режим server): команды apply/ready/optout/status/watch,
  polling-цикл подбора матчей. Веб позже поверх того же сервера без его правки.
ЭТАП 12: Наблюдение
- Event Store (append-only на бой) -> read model -> рендер кадров: live/replay
  потактово + итоговая сводка после боя. Консоль v1; браузер — позже через тот
  же Event Store, список приложений расширяем (курс).

Корабль может Стрелять
ДвигатьсяПоПрямой включает в себя MoveCommand

При Событии Collision Выполнить Обездвижить

4. РЕШЕНИЯ ПО ОТКРЫТЫМ ВОПРОСАМ PROPOSAL (внести как [решено])
- В1: команда получает сущность при выполнении (вариант B, контекст).
- В2: связь X-Y = владение конкретными сущностями в сессии.
- В5: формат реакции "При Событии X Выполнить Y".
- В6: начальное состояние — отдельный файл сценария.
- В7: останов = гибель флотилии соперника или лимит тактов (ничья).
- В9: source generator. В10: [GeneratedCode] + исключение из покрытия.

5. ПРОЦЕСС
- Каждый этап = отдельный issue + ветка на GitHub (требование курса).
- Сквозной тест сервера: две заявки -> матч -> бой -> результат в истории ->
  повторный подбор с учётом истории.
- Порядок работ: Этапы 1-2 и 7-8 параллельны (не зависят друг от друга);
  первая сквозная демонстрация сервера — на фейковом хосте боя, затем Этап 10
  подменяет заглушку реальным боем.
